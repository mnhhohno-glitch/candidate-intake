# 質問文生成品質低下の原因調査結果および是正対応

## 1. 調査結果サマリ

| 検証項目 | 結果 | 備考 |
|----------|------|------|
| LLM呼び出しの有無 | ✅ 実際に発生している | `generateWithGemini` が `fetch` で Gemini API に POST |
| base_prompt の渡し方 | ✅ system 指示として渡している | `system_instruction.parts[].text` に全文 |
| PDF テキストの渡し方 | ⚠️ 渡しているが、空のままでも呼び出していた | 抽出失敗時は `""` → userPrompt に「(なし)」で Gemini 呼び出し |
| 面談メモの渡し方 | ✅ そのまま userPrompt に含めている | `interviewMemoText` を `buildHearingQuestionTextPrompt` で結合 |
| 即時 return / モック / キャッシュ | ✅ なし | モック・スタブ・キャッシュ応答は存在しない |
| PDF 抽出 0 文字時の扱い | ❌ 不備あり | 0 文字でも Gemini を呼んでいた |

**結論（根原因）**:  
**PDF からテキストが抽出できていない、または PDF が実質渡っていない状態でも Gemini を呼び出していた**ため、プロンプトが「職種＋(なし)＋(なし)」に近く、応答が短く・汎用的になり、かつトーク数が少ないため応答が「即時」に近くなっていた。

---

## 2. 検証の詳細

### 2.1 LLM 呼び出しの検証（step_1）

- **コード**: `src/services/geminiClient.ts` の `generateWithGemini`
  - `process.env.GEMINI_API_KEY` が無い場合は throw（モックなし）
  - `fetch(\`${GEMINI_API_URL}?key=${apiKey}\`, { method: "POST", body: JSON.stringify(requestBody) })` で実際に外部 API にリクエスト
- **request 内容**: `system_instruction`（全文テキスト）と `contents[0].parts[0].text`（user プロンプト）を送信
- **即時応答の要因**: 入力トークンが少ない（PDF 本文が空）と Gemini の応答も短く・速い

### 2.2 入力ペイロードの検証（step_2）

- **base_prompt**: `specs/04_hearing_question_text_prompt.yaml` の `base_prompt` を `loadSpec.buildHearingQuestionTextPrompt` で読み、`systemInstruction = base_prompt + "\n\n---\n\n" + input_instruction` として渡している。改変・省略はしていない。
- **PDF 本文**: `extractTextFromPdf(buffer)` の戻り値 `resumePdfText` をそのまま `userPrompt` に含めている。ただし **抽出が 0 文字のときも「(なし)」として渡し、Gemini を呼んでいた**。
- **面談メモ**: `interviewLogFile.text()` で取得した文字列をそのまま `userPrompt` に含めている。
- **job_type**: FormData の `job_type` をそのまま user プロンプトに含めている。
- ファイルIDのみ送る実装・空文字を意図的に送る実装はなし。

### 2.3 PDF 処理の検証（step_3）

- **処理の有無**: `src/services/extractText.ts` の `extractTextFromPdf` で pdf-parse を使用。テキストが極端に短い場合は OCR フォールバックあり。
- **問題点**: 抽出失敗時は `catch` で `return ""`。0 文字のままでも API 側では **エラーにせず**、`resumePdfText = ""` で Gemini を呼んでいた。このとき `userPrompt` の「【候補者WEB履歴書PDF抽出テキスト】」は「(なし)」となり、LLM は履歴書を読んでいない状態で応答していた。
- 日本語・文字数については、**0 文字のときの扱いが不備**であり、正常時は十分なテキストが渡る設計。

### 2.4 プロンプトフローの検証（step_4）

- **役割**: `system_instruction` に base_prompt 全文＋input_instruction を渡している（user ロールではない）。
- **省略・要約**: なし。YAML から読み込んだ文字列をそのまま結合している。
- **base_prompt をそのまま出力する分岐**: なし。出力は Gemini の応答テキストのみ。コードブロック除去のみ実施。

## 3. 是正内容

### 3.1 必須対応（実装済み）

1. **PDF 抽出が 0 文字のときは Gemini を呼ばない**
   - `extractTextFromPdf` の結果が 0 文字の場合、`400` を返し、メッセージで「PDFからテキストを抽出できませんでした。スキャン画像のみのPDFの場合は…」と案内。
2. **PDF が実質ない場合も Gemini を呼ばない**
   - 受け取った PDF でテキスト抽出を行った結果、`resumePdfText.length === 0` のときは同上の 400 で返す。
   - 加えて、**PDF 未送信または抽出結果が空のまま**（`resumePdfText.length === 0`）のときは、Gemini を呼ばず「PDFをアップロードし、テキストが抽出できるPDFをご利用ください。」で 400 を返すようにした。
3. **診断用ログの追加**
   - 呼び出し前: `job_type`, `systemInstruction` 文字数, `userPrompt` 文字数, `resumePdfChars`, `interviewMemoChars`
   - 呼び出し後: 応答までの経過時間（ms）と出力文字数  
   → Railway 等のログで「PDF が本当に渡っているか」「応答に何秒かかっているか」を確認可能。

### 3.2 行っていないこと（品質維持のため）

- base_prompt 本文の改変は一切していない。
- 要約・短縮・ダミー応答・テンプレ返却は行っていない。
- 生成速度優先のための入力省略は行っていない。

---

## 4. 修正後の受け入れ基準の確認方法

- **PDF 内容で質問が変わる**: 異なる履歴書 PDF で「質問文を生成」を実行し、出力が明らかに変わることを確認する。
- **PDF が無い/読めないときはエラー**: テキストのない画像のみ PDF や、未アップロード時に 400 エラーまたは画面の「PDFをアップロードしてください」等が表示されることを確認する。
- **処理時間**: Railway ログで `[hearing-question-text] Gemini returned in X ms` を確認し、ある程度の遅延（数秒〜十数秒）が発生していることを確認する。
- **base_prompt がそのまま出ない**: 出力が「候補者に送る質問本文のみ」であり、プロンプトの見出しや説明がそのまま出ていないことを確認する。

---

## 5. 修正後の実際の生成例で確認すること（PDF 差し替え比較）

1. **同一 job_type・同一面談メモで PDF だけ差し替え**
   - PDF-A で生成 → 質問内容をメモ
   - PDF-B（別候補者）で生成 → 質問内容が PDF-A と異なることを確認
2. **同一 PDF で job_type または面談メモだけ変更**
   - 職種や面談メモの差分が質問に反映されていることを確認
3. **ログ確認**
   - `resumePdfChars` が 0 でないこと
   - `Gemini returned in X ms` で X が数千 ms 以上であること（即時でないこと）

以上で、品質低下の原因は「PDF 本文が空のまま LLM を呼んでいたこと」と特定し、PDF が確実に渡る場合にのみ生成するよう是正した。
