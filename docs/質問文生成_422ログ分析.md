# 質問文生成 422 / 400 エラー — Railway ログ分析と原因

## 400「PDFからテキストを抽出できませんでした」について

**スキャンではない PDF でも 400 になる理由**

- 400 は「**サーバー側で PDF から 1 文字も取れなかった**」ときに返しています（抽出結果が 0 文字）。
- スキャン画像でなくても、次のような場合に 0 文字になることがあります。
  - **pdf-parse** がその PDF の形式・バージョン・フォント埋め込みに対応していない
  - パスワード保護・制限付き PDF
  - サーバー環境（Node / メモリ）の制約で例外が発生し、`extractTextFromPdf` が空文字を返した
  - テキストレイヤーが 0 で OCR フォールバックも 0 文字（前回ログでは 38 文字だったが、環境や PDF 次第で 0 の可能性あり）

**仕様変更：システムDL PDF 向けの pdfjs-dist フォールバック（2026年2月）**

- **抽出の流れ**は次の 3 段階です。  
  1) **pdf-parse** でテキスト取得 → 2) **pdfjs-dist** でテキスト取得（0 文字・極端に短いときのみ） → 3) まだ短い場合 **OCR**
- システムからダウンロードした PDF で pdf-parse が 0 文字を返す場合、**2) pdfjs-dist** でテキストが取れる可能性があります（cMapUrl / standardFontDataUrl 指定済み）。  
- 同じ PDF で 400 が続く場合は、サーバーログで `[extractText] pdfjs-dist fallback succeeded` の有無を確認してください。

**過去の障害：cMapUrl に末尾スラッシュ必須（解消済み）**

- ログに `Invalid factory url: "file:///app/node_modules/pdfjs-dist/cmaps" must include trailing slash` が出ていた場合、pdfjs-dist が cMapUrl / standardFontDataUrl に **末尾スラッシュ** を要求しているためでした。`extractTextPdfJs.ts` と `extractTextPdfOcr.ts` で URL 末尾にスラッシュを付与するよう修正済みです。
- **OCR の getDocument 失敗時**: `extractTextPdfOcr.ts` で、CMap 付きで getDocument が失敗した場合（上記 Invalid factory url など）は **CMap なしで再試行**するフォールバックを追加済みです。
- **ページ数が 0 のときも OCR を試す**: `extractText.ts` で、pdf-parse / pdfjs のどちらからもページ数が取れない場合でも、テキストが短くバッファがあれば OCR を呼ぶように変更済みです（OCR 内で getDocument してページ数を取得）。

**過去の障害：CMap 読み込み失敗で pdfjs が 0 文字 + ゲートで 422（解消済み）**

- ログに `Unable to load binary CMap at: file:///app/node_modules/pdfjs-dist/cmaps/UniJIS-UCS2-H.bcmap` が出て、`[extractTextPdfJs] Done, pages: 3 chars: 0` となり、OCR のみ 38 文字取れて `gate_checks_failed resumePdfChars=38 < 101` で 422 になっていた。
- **対応1**: ゲートのデフォルトを **1** に変更（0 文字以外は通過）。38 文字でも通過する。

**Railway 本番ログで CMap / Gemini Vision の警告が出る場合（既知・非致命）**

- `Warning: loadFont - translateFont failed: ... UniJIS-UCS2-H.bcmap` や `[Gemini] Empty candidates` / `Gemini Vision page 1 failed` がデプロイログに出ることがあります。
- このときも **PDF インライン経路**（`Gemini PDF inline done`）と **Step A / Step B** で質問文は生成されており、処理は成功しています。Vision 失敗時は PDF テキストで続行する設計です。
- ビルドが完了し `Ready in 333ms` が出ていればアプリは起動済みです。「Deployment failed to build」が表示されていても、別デプロイの状態や表示のずれの可能性があるため、最新コミットで再デプロイを試してください。
- **対応2**: pdfjs で CMap ありで 0 文字のとき、**CMap なしで再試行**するフォールバックを追加。
- **Buffer() DeprecationWarning**: 依存パッケージ（pdf-parse / tesseract 等）内のため、当リポジトリのコード変更では解消できません。

**対処の目安**

- 「テキストが選択・コピーできる」形式の PDF で再度お試しください。
- 別のアプリで同じ PDF を「名前を付けて保存」し直してからアップロードすると通ることがあります。
- それでも 400 の場合は、サーバーログで `[extractText]` や `[hearing-question-text] PDF extraction returned 0` を確認すると原因の切り分けになります。

## 推奨する PDF の形式・作り方

**ブラウザのコンソールについて**

- `runtime.lastError`・`service-worker`・`Receiving end does not exist`・`No tab with id` などは **ブラウザ拡張機能** のエラーです。本アプリの不具合ではありません。
- 本アプリに関係するのは **`/api/intake/hearing-question-text` の 400** のみです。

**どんな PDF が向いているか**

- サーバーでは **pdf-parse** で「テキストレイヤー」を読んでいます。**テキストが埋め込まれた PDF** で、かつライブラリが解釈できる形式が理想です。
- **Adobe Acrobat で作成・保存した PDF** は、これまで問題なく読めていることが多いです（形式の互換性が高いため）。
- **Microsoft Edge の「PDF に保存」や「印刷 → PDF」** は、内部のエンコーディングやフォントの埋め方の違いで、pdf-parse が 0 文字と判断することがあります。Edge で作り直しても 400 が続く場合は、別の作り方をお試しください。

**おすすめの作り方（優先順）**

1. **Adobe Acrobat** で「名前を付けて保存」や「PDF として保存」したもの（従来どおり）
2. **Google Chrome** の「印刷 → 送信先: PDF に保存」（Web 履歴書を PDF にする場合）
3. **Word / Excel** の「ファイル → 名前を付けて保存 → PDF」
4. **Windows の「Microsoft Print to PDF」** で印刷して PDF にしたもの

**避けたほうがよいもの**

- スキャンした画像だけの PDF（画像のみでテキストレイヤーがない）
- パスワード・制限付き PDF
- Edge で「PDF に保存」したものは、上記を試したうえでも 400 になる場合は別手段を検討

## 422 エラー — Railway ログ分析

## ログから分かったこと

該当ログ（東 裕太郎さん PDF アップロード時）では次のように記録されていました。

| 段階 | 内容 |
|------|------|
| **PDF テキストレイヤー** | `buffer=7720 bytes, pages=3, extracted=0 chars` → **0 文字** |
| **OCR フォールバック** | 実行され、`OCR done, pages: 3 chars: 38` → **38 文字のみ** |
| **フォント/CMap 警告** | `Ensure that the cMapUrl and cMapPacked API parameters are provided` |
| **ゲート** | `gate_checks_failed reason= resumePdfChars=38 < 101` → **422 返却** |

## 原因の整理

1. **テキストレイヤーが 0 文字**
   - この PDF は画像ベース（スキャン）か、テキストが埋め込まれていない形式の可能性が高いです。
   - そのため `pdf-parse` では 1 文字も取れていません。

2. **OCR が 38 文字しか取れていない**
   - 3 ページあるのに 38 文字だけということは、**描画時にフォント/CMap の不足**で日本語が正しく描画されておらず、OCR がほとんど読めていない可能性があります。
   - ログの `cMapUrl and cMapPacked API parameters are provided` は、日本語等のフォント用 CMap が未指定だったことを示しています。

3. **ゲートの判定**
   - 抽出結果が **38 文字** のため、「101 字以上で通過」のゲートで **正しく NG** となり、422 が返っています。
   - ゲートの閾値が悪いのではなく、「サーバー上で実際に取れた文字数が 38 だった」ことが原因です。

## 実施した対応

- **OCR 時の cMap / standardFontDataUrl を指定**
  - `extractTextPdfOcr.ts` で、`pdfjs-dist` の `getDocument` に  
    `cMapUrl`・`cMapPacked`・`standardFontDataUrl` を渡すように変更しました。
  - Railway 上でも日本語が正しく描画され、OCR で取れる文字数が増える可能性があります。

## 運用上の注意

- **テキストレイヤー付きの PDF を推奨**
  - スキャンではなく、パソコンで作成・保存した「テキスト付き」の PDF だと、テキスト抽出で多くの文字が取れ、ゲートも通りやすくなります。
- **422 が出た場合**
  - レスポンスの `detail` に「抽出文字数: ○○ 文字」が入るようになっています。  
    - 38 のように少ない → 抽出/OCR 環境の制約が疑われます。  
    - 上記 cMap 対応のデプロイ後、同じ PDF で再試行してみてください。
