# 質問文生成の「ゲート」について

## ゲートとは何か（役割）

**ゲート**は、PDF からテキストを抽出した**直後**に、「この抽出結果で質問文生成に進んでよいか」を判定する**品質の関所**です。

- **通過した場合**: そのまま Step A（構造化抽出）→ Step B（質問文生成）へ進む。
- **通過しなかった場合**: **生成処理は行わず**、HTTP 422 と「PDFテキスト抽出が不十分で…」というメッセージを返す。

### ゲートがもたらしている役割

1. **不良な抽出結果で LLM を呼ばない**
   - 抽出テキストが極端に短い・空に近い状態で生成すると、以前のように「資料を読んでいない」ような汎用出力になりやすい。
   - ゲートで「ある程度の情報量がある抽出結果」だけを通すことで、**「読めるだけの材料がある」状態のときだけ**生成に進む。

2. **ユーザーへの早いフィードバック**
   - 抽出が不十分な PDF（スキャン画像のみで OCR が効いていない、破損、ほぼ空白など）をそのまま Step A/B に回すと、時間と API コストをかけたうえで低品質な結果になる。
   - ゲートで早めに止めて 422 を返すことで、「この PDF では十分なテキストが取れていません」と**すぐに伝えられる**。

3. **コスト・時間の無駄を減らす**
   - Step A と Step B で 2 回 Gemini を呼ぶため、明らかに材料不足の PDF では呼ばないようにする。

## 「文字数」で判定している理由（考え方）

ゲートでは、**「抽出テキストの文字数が閾値以上か」**を一つの条件にしています。

### 重要：判定対象は「PDF 1通あたりの全体」だけ

- **項目ごと・ページごと・セクションごとの文字数は見ていません。**
- 判定に使うのは **「その PDF から抽出したテキスト全体を 1 つにつなげた長さ」** だけです。
- つまり「履歴書 PDF を 1 通アップロードしたとき、その 1 通分の抽出結果が何文字か」だけをチェックしています。

### ゲートの考え方（抽出エラー疑いの検知）

- **抽出結果が数十〜数百文字程度**のときは、
  - PDF のほうは 1000 字以上あるのに、**読み取りの段階で何かしらのエラーや失敗**（画像のみでテキストが取れていない、OCR が効いていない、破損・文字化けなど）があり、
  - その状態で生成に進むと**品質低下が懸念される**
  → そういう「**抽出が明らかに不十分**」なケースだけをゲートで止めたい、という考え方です。

- **PDF 全体**として、抽出結果が 500 字や 1000 字ある場合は正常な範囲なので、ゲートを通して生成に進めます。
- **100 文字以下**（0〜100 字）をエラー対象とし、101 字以上で通過します。平均よりしっかり書いてある PDF が誤って弾かれないよう、閾値は低めにしている。

### なぜ文字数なのか

- **「中身を解釈しない」指標にしたいため**
  - ゲートの段階では、まだ「資格が何件」「住所がどこ」といった意味解析はしていない（それは Step A の役割）。
  - 文字数は**解釈不要**で、「抽出結果の量が足りているか」の**粗いが安定した目安**になる。

- **「抽出の失敗・不十分」の目安にするため**
  - **100 文字以下**（0〜100 字）＝ 読み取りエラー・ほぼ空白・破損の可能性が高い → ゲートで止める。
  - 101 字以上は通過。平均より多く書いてある PDF が誤って弾かれないよう、数字は低め（100 文字以下をエラー対象）にしている。

- **実装が単純で、運用で調整しやすいため**
  - 閾値は環境変数 `HEARING_GATE_MIN_CHARS` で変更可能（デフォルト **1**。1 字以上で通過）。
  - 「何文字以上を通すか」だけを変えればよい。

### デフォルト 1 字以上で通過とする理由

- 判定は **PDF 1 通あたりの抽出テキスト全体の文字数**のみ。項目ごとの文字数ではありません。
- 本番環境で **pdfjs の CMap 読み込みに失敗**すると、テキスト抽出が 0 文字になり、OCR のみで 38 文字などになる PDF がある。その場合でも 422 にせず生成まで進めるため、**0 文字以外は通過**（デフォルト閾値 1）にしている。
- **0 文字**→ エラー（ゲートで止める）。**1 字以上**→ 通過。厳格にしたい場合は `HEARING_GATE_MIN_CHARS=101` 等を設定。

## ゲートの判定内容（現在の実装）

| 条件 | デフォルト | 説明 |
|------|------------|------|
| **文字数** | 1 字以上で通過（0 文字のみエラー） | PDF 1 通の抽出テキスト全体。本番で OCR のみ 38 文字になる PDF も通過。厳格化時は `HEARING_GATE_MIN_CHARS=101` 等を設定。 |
| **資格キーワード** | チェックしない（スキップ） | 環境変数 `HEARING_GATE_QUALIFICATION_SUBSTRINGS` を設定したときだけ、その文字列のいずれかが含まれるかをチェック。 |
| **住所キーワード** | チェックしない（スキップ） | 環境変数 `HEARING_GATE_ADDRESS_SUBSTRINGS` を設定したときだけ、同様にチェック。 |

求職者は多数いるため、**デフォルトでは「文字数」だけ**で判定し、特定のキーワードは「必要に応じて env で有効化する」形にしている。

## 処理の流れのなかでの位置づけ

```
PDF アップロード
    ↓
PDF テキスト抽出（extractTextFromPdf）
    ↓
【ゲート】← ここで「文字数 ≥ 閾値」等をチェック
    ├─ NG → 422 を返して終了（Step A/B は呼ばない）
    └─ OK → Step A（構造化抽出）→ Step B（質問文生成）→ 出力自己検査
```

ゲートは**「抽出の品質が、生成に使うのに足りているか」を簡易に判定する関所**であり、  
**文字数は「その足りなさ」を測るための、解釈不要で調整しやすい指標**として使っている、という考え方です。
